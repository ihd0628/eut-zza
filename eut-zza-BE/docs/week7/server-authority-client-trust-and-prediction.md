# 서버의 최종 결정권, Trust Boundary, Client Prediction

## 이 문서의 목표

멀티플레이 게임에서 서버가 최종 결정해야 하는 상태와 클라이언트에 맡길 계산을 구분한다. 또한 Trust Boundary가 단순히 물리적인 클라이언트·서버 경계가 아니라 신뢰 수준이 달라지는 보안상의 경계라는 점을 이해한다.

읏짜는 다음 아키텍처를 유지한다.

```text
멀티플레이의 공유 상태와 경기 운영
→ 서버가 최종 결정

노트 판정과 점수 계산
→ 각 클라이언트가 수행

경기 종료 후 최종 결과
→ 클라이언트가 한 번에 서버로 전송
→ 서버는 점수의 진실성을 신뢰하고 저장
```

서버가 노트별 입력을 받아 리듬 판정을 다시 실행하는 구조로 변경하지 않는다.

---

## 1. Authoritative Server

Authoritative는 특정 상태에 대한 최종 결정권을 가진다는 뜻이다.

클라이언트와 서버의 주장이 다르면 해당 상태의 최종 결정권자가 어떤 쪽인지에 따라 최종 상태를 정한다.

```text
Client:
"나는 이 방의 방장이다."

Server:
"현재 방장은 user-1이고 요청자는 user-3이다."

최종 결정:
서버 상태를 사용하고 요청을 거절한다.
```

Authoritative Server가 게임의 모든 계산을 서버에서 실행해야 한다는 뜻은 아니다. 상태 종류마다 최종 결정권을 다르게 설계할 수 있다.

### 읏짜에서 서버가 결정하는 상태

- 인증된 사용자 신원
- 방 참가자와 방장
- 방 최대 인원 4명
- 선택된 곡과 난이도
- 준비 상태와 음원 준비 상태
- 경기 시작 가능 여부
- Game Session과 Game Player ID
- 서버 기준 경기 시작 시각
- 경기 진행·종료 상태
- 참가자별 결과 제출 여부
- 전체 참가자의 최종 순위와 공동 우승
- PostgreSQL에 저장할 영속 결과 row

### 읏짜에서 클라이언트가 계산하는 상태

- 노트별 판정
- PERFECT, GREAT, GOOD, MISS 개수
- 현재 Combo와 최대 Combo
- 최종 점수
- 로컬 게임 완료

```text
멀티플레이 경기 운영
→ Server Authoritative

리듬게임 판정과 점수 계산
→ Client Calculation
→ Server Trusts Final Result
```

## 2. 서버가 다시 검사해야 하는 이유

React 화면은 보안 경계가 아니다. 사용자는 개발자 도구에서 JavaScript를 실행하거나 프론트엔드 UI를 거치지 않고 HTTP·WebSocket 요청을 만들 수 있다.

```text
프론트엔드에서 일반 참가자의 곡 변경 버튼 숨김
→ 올바른 UI와 사용성 제공

서버에서 요청자의 방장 권한 검사
→ 실제 접근 통제
```

클라이언트가 경기 시작을 요청하면 서버는 다음 조건을 자신의 상태로 확인한다.

```text
요청자가 방장인가?
참가자가 2~4명인가?
모든 참가자가 준비됐는가?
모든 참가자의 음원이 준비됐는가?
이미 시작 중인 경기가 없는가?
```

클라이언트가 조건을 만족한다고 주장하는 것만으로 경기를 시작하지 않는다.

## 3. Trust Boundary의 정확한 정의

Trust Boundary는 신뢰 수준이나 보안 권한이 서로 다른 두 영역 사이에서 데이터 또는 제어권이 넘어가는 지점이다.

```text
사용자가 통제하는 Browser
             │
             │ Trust Boundary
             ↓
서비스가 통제하는 Backend
```

경계를 넘어온 데이터는 이전 영역에서 만들어졌다는 이유만으로 믿지 않고, 데이터를 받는 영역의 규칙으로 다시 확인해야 한다.

Trust Boundary는 클라이언트와 서버 사이에만 존재하는 것이 아니다.

- 일반 사용자와 관리자 기능
- 우리 서버와 외부 API
- 서비스 A와 서비스 B
- 애플리케이션과 외부 결제 시스템
- 권한이 서로 다른 프로세스나 계정

핵심은 물리적인 위치가 아니라 신뢰 수준과 권한이 달라지는가이다.

## 4. Trust Boundary에서 수행하는 검사

### Authentication

요청자가 누구인지 확인한다.

```text
로그인한 사용자인가?
세션이 유효한가?
```

### Authorization

그 사용자에게 요청한 작업을 할 권한이 있는지 확인한다.

```text
방장인가?
방 참가자인가?
이 Game Player의 소유자인가?
```

### Validation

전달된 값의 형식과 범위를 확인한다.

```text
beatmapId가 올바른 형식인가?
score가 유효한 숫자인가?
difficulty가 허용된 값인가?
```

### Domain Invariant

애플리케이션 규칙을 만족하는지 확인한다.

```text
방 인원이 4명을 넘지 않는가?
모두 준비했는가?
이미 종료된 경기가 아닌가?
결과를 중복 제출하지 않았는가?
```

### 시스템 보호

```text
Request Body가 지나치게 크지 않은가?
요청을 비정상적으로 반복하지 않는가?
SQL parameter를 사용해 값을 전달하는가?
```

## 5. TypeScript와 HTTPS가 보장하지 않는 것

TypeScript 타입은 개발 중 코드의 실수를 줄여주지만 런타임 네트워크 데이터의 진실성을 보장하지 않는다.

```ts
type Result = {
  score: number;
};
```

사용자는 프론트엔드 코드를 거치지 않고 임의의 JSON 요청을 만들 수 있다. 서버는 Schema 등으로 네트워크 입력을 다시 검사해야 한다.

로그인도 사용자가 누구인지 확인할 뿐 그 사용자가 보내는 모든 데이터가 정직하거나 모든 권한을 가졌다는 뜻은 아니다.

HTTPS는 전송 중 도청과 변조를 방지하지만 사용자가 처음부터 거짓 값을 보내는 것을 막지 않는다.

```text
조작된 score를 HTTPS로 안전하게 전송
→ 전송은 보호됨
→ score의 진실성은 보장되지 않음
```

## 6. 점수를 신뢰해도 검사해야 하는 것

현재 읏짜는 클라이언트가 계산한 점수의 실제 진실성을 신뢰한다. 그렇더라도 결과를 저장할 자격과 데이터 정합성은 서버가 검사한다.

```text
서버가 검사하는 것

- 로그인 여부
- Game Player의 소유자
- Game Session 참가 여부
- Request Body의 구조와 자료형
- 음수가 될 수 없는 값의 범위
- 결과 중복 제출 여부
- 동일한 재시도인지 다른 결과의 충돌인지
- DB Foreign Key와 Unique Constraint
```

서버가 검사하지 않는 것은 다음과 같다.

```text
- 사용자가 실제로 해당 노트를 눌렀는가?
- 판정 시각이 음원 시각과 정확히 일치하는가?
- PERFECT 개수가 실제 플레이 결과인가?
- 점수가 조작되지 않았는가?
```

신뢰는 전체를 믿거나 전체를 거부하는 이분법이 아니다. 데이터에 포함된 각각의 주장을 어떤 근거로 검증하거나 의도적으로 신뢰할지 결정하는 것이다.

## 7. Client Prediction과 현재 읏짜의 차이

전통적인 Client Prediction은 서버 응답을 기다리는 동안 클라이언트가 예상 결과를 먼저 화면에 적용하는 기법이다.

```text
클라이언트가 예상 결과를 즉시 적용
→ 서버도 같은 상태를 계산
→ 서버가 확정 상태 반환
→ 다르면 클라이언트가 서버 상태로 보정
```

클라이언트 예상과 서버 확정 결과가 다를 때 수정하는 과정을 Reconciliation이라고 한다.

현재 읏짜의 노트 판정은 서버가 다시 계산하지 않는다.

```text
클라이언트가 노트 판정
→ 화면에 즉시 표시
→ 클라이언트가 최종 점수 계산
→ 서버로 최종 결과 전송
→ 서버가 결과를 신뢰
```

서버의 판정 확정과 Reconciliation이 없으므로 엄밀한 의미의 Client Prediction보다는 클라이언트 로컬 판정과 결과 신뢰 구조라고 표현하는 것이 정확하다.

| 데이터 | 최종 결정권 |
|---|---|
| 로그인 사용자 | 서버 |
| 방 참가자 | 서버 |
| 방장 | 서버 |
| 곡·난이도 | 서버 |
| 준비 상태 | 서버 |
| 경기 시작 여부·시각 | 서버 |

| 최종 순위·공동 우승 | 서버 |
| 영속 결과 row | 서버와 PostgreSQL |

## 최종 정리

- Authoritative Server는 모든 계산을 서버에서 한다는 뜻이 아니라 특정 상태의 최종 결정권이 서버에 있다는 뜻이다.
- Trust Boundary는 신뢰 수준이나 권한이 다른 영역 사이에서 데이터와 제어권이 넘어가는 지점이다.
- Trust Boundary를 통과한 데이터는 인증, 권한, 형식, 도메인 규칙을 다시 확인한다.
- TypeScript, 로그인, HTTPS만으로 클라이언트가 보낸 내용의 진실성이 보장되지는 않는다.
- 읏짜는 공유 경기 상태를 서버가 결정하고, 노트 판정과 점수는 클라이언트가 계산한 결과를 신뢰한다.
- 현재 노트 판정에는 서버의 재계산과 Reconciliation이 없으므로 엄밀한 Client Prediction 구조가 아니다.
